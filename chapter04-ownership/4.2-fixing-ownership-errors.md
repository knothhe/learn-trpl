# Fixing Ownership Errors

原文：https://rust-book.cs.brown.edu/ch04-03-fixing-ownership-errors.html

这一节讲一个实际 Rust 开发中非常重要的能力：当 borrow checker 拒绝你的代码时，应该怎么修。

核心思路不是“怎么哄编译器通过”，而是先判断：

```text
这个程序本身是真的不安全，还是 Rust 当前的 borrow checker 不够聪明？
```

如果程序本身不安全，就要理解不安全的根本原因，然后调整 API 或数据流。

如果程序本身安全，但 borrow checker 不能证明它安全，就要换一种 Rust 能理解的写法，或者使用标准库提供的安全抽象。

## 总体判断方法

修 ownership error 时，先问两个问题：

1. 数据应该活多久？
2. 谁负责释放这份数据？

然后再问：

1. 这个函数真的需要 ownership 吗？
2. 这个函数只是读数据，还是要修改数据？
3. 引用是否和 mutation 重叠了？
4. 是否试图从引用后面 move 出数据？
5. borrow checker 是不是把两个实际不同的位置当成了同一个位置？

## Unsafe Program：返回栈上数据的引用

错误代码：

```rust
fn return_a_string() -> &String {
    let s = String::from("Hello world");
    &s
}
```

这个函数想返回 `s` 的引用。

问题是 `s` 是函数内部的局部变量，存在当前函数的 stack frame 里。
函数返回后，`s` 会被释放。

所以返回 `&s` 会产生 dangling reference：

```text
return_a_string 返回后，引用还在，但它指向的数据已经没了。
```

Rust 会拒绝这个程序。

这类问题的本质是：

```text
被引用的数据活得不够久。
```

## 修法一：返回所有权

最直接的修法是把返回类型从 `&String` 改成 `String`：

```rust
fn return_a_string() -> String {
    let s = String::from("Hello world");
    s
}
```

这样不是返回引用，而是把 `String` 的所有权移动给调用者。

调用者拿到的是拥有权，负责之后释放它。

适用场景：

- 函数内部创建了一份新数据。
- 调用者之后需要拥有这份数据。
- 不想让返回值依赖函数内部的局部变量。

这是最常见、最自然的修法。

## 修法二：返回字符串字面量

如果字符串内容固定，而且不需要修改，可以返回字符串字面量：

```rust
fn return_a_string() -> &'static str {
    "Hello world"
}
```

`"Hello world"` 是字符串字面量，类型是 `&'static str`。

`'static` 表示这份数据在整个程序运行期间都有效。

适用场景：

- 返回固定文本。
- 不需要 heap allocation。
- 不需要修改字符串内容。

注意这里返回的是 `&str`，不是 `&String`。

## 修法三：使用 `Rc`

还有一种方式是使用 reference-counted pointer：

```rust
use std::rc::Rc;

fn return_a_string() -> Rc<String> {
    let s = Rc::new(String::from("Hello world"));
    Rc::clone(&s)
}
```

`Rc<T>` 是引用计数智能指针。

`Rc::clone(&s)` 不会复制 `String` 的内容，只会复制一个指向同一份数据的智能指针，并增加引用计数。

当最后一个 `Rc` 被 drop 时，数据才会被释放。

适用场景：

- 同一份数据需要有多个拥有者。
- 无法简单地用单一 ownership 表达生命周期。
- 数据只需要在单线程内共享。

注意：`Rc<T>` 会把一部分生命周期检查从编译期转到运行时引用计数。

## 修法四：让调用者提供输出位置

也可以让调用者传入一个可变引用作为输出位置：

```rust
fn return_a_string(output: &mut String) {
    output.replace_range(.., "Hello world");
}
```

调用者负责创建 `String`，函数只负责把内容写进去。

适用场景：

- 调用者想控制分配。
- 希望复用已有 buffer。
- 对性能和内存分配有比较细的控制。

这种写法有时更高效，但 API 会更啰嗦。

## 这个案例的关键

面对：

```rust
fn f() -> &T
```

要立刻问：

```text
这个引用指向的数据是谁拥有的？
它是否比返回的引用活得更久？
```

如果引用指向函数内部局部变量，通常就是错的。

## Unsafe Program：权限不够

下面看另一个常见错误：试图修改只读引用背后的数据。

假设我们想写一个函数，把名字列表拼成完整名字，并加上 title：

```rust
fn stringify_name_with_title(name: &Vec<String>) -> String {
    name.push(String::from("Esq."));
    let full = name.join(" ");
    full
}
```

这个不能编译。

原因是 `name` 的类型是：

```rust
&Vec<String>
```

这是不可变引用，只能读，不能写。

但 `name.push(...)` 需要 `W` 权限，也就是写权限。

## 为什么这个程序不安全

看起来只是加了一个字符串，为什么 Rust 要拒绝？

因为外部可能已经有指向 `name` 内部元素的引用：

```rust
fn stringify_name_with_title(name: &Vec<String>) -> String {
    name.push(String::from("Esq.")); // 假设允许这样做
    name.join(" ")
}

fn main() {
    let mut name = vec![String::from("Ferris")];
    let first = &name[0];

    let full = stringify_name_with_title(&name);

    println!("{first}");
    println!("{full}");
}
```

如果 `push` 导致 `Vec` 重新分配，`first` 可能指向已经释放的旧内存。

所以 Rust 不允许通过不可变引用修改 `Vec`。

## 不推荐修法：改成 `&mut Vec<String>`

一种直接修法是：

```rust
fn stringify_name_with_title(name: &mut Vec<String>) -> String {
    name.push(String::from("Esq."));
    let full = name.join(" ");
    full
}
```

这样可以编译，但 API 语义不好。

函数名 `stringify_name_with_title` 听起来像是“生成一个字符串”，调用者通常不期待原始 `Vec` 被修改。

如果函数真的要修改输入，更合理的名字可能是：

```rust
fn add_title_to_name(name: &mut Vec<String>)
```

API 的权限应该匹配调用者预期。

## 不推荐修法：拿走 ownership

另一种修法是让函数拿走 `Vec`：

```rust
fn stringify_name_with_title(mut name: Vec<String>) -> String {
    name.push(String::from("Esq."));
    let full = name.join(" ");
    full
}
```

这也能编译，但通常也不是好 API。

因为调用者调用之后，原来的 `name` 就不能用了：

```rust
let name = vec![String::from("Ferris")];
let full = stringify_name_with_title(name);

println!("{name:?}"); // error
```

Rust 里很少无故让函数拿走 `Vec`、`String` 这类 heap-owning 数据结构的所有权。

如果只是读取，应该用引用。

## 可行修法：clone 一份局部副本

保持 API 为只读引用，然后在函数内部 clone：

```rust
fn stringify_name_with_title(name: &Vec<String>) -> String {
    let mut name_clone = name.clone();
    name_clone.push(String::from("Esq."));
    let full = name_clone.join(" ");
    full
}
```

这样修改的是本地副本，不会影响调用者的 `Vec`。

缺点是 `clone` 会复制整个 `Vec`，包括里面每个 `String` 的内容。

这可能产生不必要的内存分配和拷贝。

## 更好的修法：改变函数体的数据流

这个函数其实不需要修改 `Vec`。

可以先 join，再往结果字符串追加 title：

```rust
fn stringify_name_with_title(name: &Vec<String>) -> String {
    let mut full = name.join(" ");
    full.push_str(" Esq.");
    full
}
```

这通常是更好的写法。

原因：

- `name` 只需要读权限。
- `join` 本来就会生成新的 `String`。
- title 追加到新生成的 `String` 上，不需要动原始 `Vec`。
- API 符合调用者预期。

这个案例的关键是：

```text
不要为了让代码编译而提高函数权限。
函数应该只要求它真正需要的权限。
```

## Unsafe Program：aliasing 和 mutation 同时发生

再看一个 `Vec` 相关例子。

需求：找到 `dst` 里最长的字符串，然后把 `src` 中比它更长的字符串加入 `dst`。

错误写法大概是：

```rust
fn add_big_strings(dst: &mut Vec<String>, src: &[String]) {
    let largest: &String = dst.iter().max_by_key(|s| s.len()).unwrap();

    for s in src {
        if s.len() > largest.len() {
            dst.push(s.clone());
        }
    }
}
```

这个不能编译。

`largest` 是指向 `dst` 内部元素的引用。

然后 `dst.push(...)` 试图修改 `dst`。

这正好违反了前一节的原则：

```text
data should never be aliased and mutated at the same time
```

## 为什么这个程序不安全

`largest` 指向 `dst` 内部的某个 `String`。

`dst.push(...)` 可能导致 `Vec` 重新分配。

如果重新分配发生，`largest` 就可能指向失效内存。

所以 Rust 拒绝。

根本修法是：

```text
缩短 largest 对 dst 的借用生命周期，不要让它和 dst.push(...) 重叠。
```

## 修法一：clone `largest`

```rust
fn add_big_strings(dst: &mut Vec<String>, src: &[String]) {
    let largest: String = dst.iter().max_by_key(|s| s.len()).unwrap().clone();

    for s in src {
        if s.len() > largest.len() {
            dst.push(s.clone());
        }
    }
}
```

这里 `largest` 是一个新的 `String`，不再借用 `dst`。

因此后面可以安全地修改 `dst`。

缺点是 clone 可能有性能成本。

## 修法二：先收集，再修改

```rust
fn add_big_strings(dst: &mut Vec<String>, src: &[String]) {
    let largest: &String = dst.iter().max_by_key(|s| s.len()).unwrap();

    let to_add: Vec<String> = src
        .iter()
        .filter(|s| s.len() > largest.len())
        .cloned()
        .collect();

    dst.extend(to_add);
}
```

这里分成两个阶段：

1. 借用 `dst`，计算出要添加的内容。
2. 借用结束后，再修改 `dst`。

缺点是需要额外分配一个 `to_add`。

## 修法三：只拷贝需要的信息

这个例子中，我们其实只需要最长字符串的长度，不需要字符串本身。

所以最好的写法通常是：

```rust
fn add_big_strings(dst: &mut Vec<String>, src: &[String]) {
    let largest_len: usize = dst.iter().max_by_key(|s| s.len()).unwrap().len();

    for s in src {
        if s.len() > largest_len {
            dst.push(s.clone());
        }
    }
}
```

`largest_len` 是 `usize`，它是 copy 类型，不再借用 `dst`。

所以后面可以修改 `dst`。

这个修法通常最 idiomatic，也最 performant。

## 这个案例的关键

当引用和 mutation 冲突时，常见修法是缩短借用生命周期：

- clone 引用指向的数据。
- 先计算结果，再修改原数据。
- 只复制真正需要的字段或长度。
- 调整代码顺序，让引用最后一次使用发生在 mutation 之前。

## Unsafe Program：从集合中 copy vs move

先看一个能编译的例子：

```rust
fn main() {
    let v: Vec<i32> = vec![0, 1, 2];
    let n_ref: &i32 = &v[0];
    let n: i32 = *n_ref;

    println!("{n}");
}
```

`i32` 是 `Copy` 类型。

`let n = *n_ref;` 会复制一个整数出来，不会移动 ownership。

但如果把元素类型换成 `String`：

```rust
fn main() {
    let v: Vec<String> = vec![String::from("Hello world")];
    let s_ref: &String = &v[0];
    let s: String = *s_ref;

    println!("{s}");
}
```

这不能编译。

错误类似：

```text
cannot move out of `*s_ref` which is behind a shared reference
```

## 为什么不能从 shared reference 后面 move

`v` 拥有里面的 `String`。

`s_ref` 只是一个不可变引用，不拥有数据。

如果允许：

```rust
let s: String = *s_ref;
```

那就等于把 `String` 从 `Vec` 里移动出来。

但 `Vec` 仍然以为自己拥有这个 `String`。

最终可能出现 double free：

```text
s 被 drop 时释放字符串
v 被 drop 时再次释放同一个字符串
```

所以 Rust 禁止从不可变引用后面 move 出非 `Copy` 类型。

## Copy 类型和非 Copy 类型

大致规则：

- `i32` 不拥有 heap data，可以 copy。
- `String` 拥有 heap data，不能隐式 copy。
- `&String` 不拥有 heap data，可以 copy。

例子：

```rust
fn main() {
    let x = 1;
    let y = x;

    println!("{x} {y}"); // ok, i32 is Copy
}
```

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1;

    println!("{s1}"); // error, String moved
}
```

引用通常可以 copy：

```rust
fn main() {
    let s = String::from("hello");

    let r1 = &s;
    let r2 = r1;

    println!("{r1} {r2}"); // ok
}
```

一个重要例外是 mutable reference。

```rust
fn main() {
    let mut n = 0;
    let a = &mut n;
    let b = a;

    // println!("{a}"); // error
    println!("{b}");
}
```

`&mut T` 不能 copy。

`let b = a;` 会 move 这个可变引用。

这样可以防止同一时间出现两个可用的可变引用。

## 安全访问 `Vec<String>` 元素的方式

方式一：只借用，不拿 ownership。

```rust
fn main() {
    let v: Vec<String> = vec![String::from("Hello world")];
    let s_ref: &String = &v[0];

    println!("{s_ref}!");
}
```

方式二：clone 一份，获得自己的 ownership。

```rust
fn main() {
    let v: Vec<String> = vec![String::from("Hello world")];
    let mut s: String = v[0].clone();

    s.push('!');

    println!("{s}");
}
```

方式三：使用集合方法真正移出元素。

```rust
fn main() {
    let mut v: Vec<String> = vec![String::from("Hello world")];
    let mut s: String = v.remove(0);

    s.push('!');

    println!("{s}");
    assert!(v.len() == 0);
}
```

`remove(0)` 会把元素从 `Vec` 中移出，同时维护 `Vec` 的内部状态。

这和通过 `*s_ref` 偷偷 move 出来不同。

## Safe Program：修改 tuple 的不同字段

前面的例子都是程序本身确实不安全。

但有时程序是安全的，Rust 仍然会拒绝。

先看一个 Rust 能理解的安全例子：

```rust
fn main() {
    let mut name = (String::from("Ferris"), String::from("Rustacean"));

    let first = &name.0;
    name.1.push_str(", Esq.");

    println!("{first} {}", name.1);
}
```

这里借用的是 `name.0`，修改的是 `name.1`。

Rust 能够区分 tuple 的不同字段，所以允许这段代码。

权限上可以理解为：

- `&name.0` 借用了 `name.0`。
- `name.0` 暂时失去 `W` 和 `O` 权限。
- 整个 `name` 也不能被整体 move。
- 但 `name.1` 仍然可以写。

## Safe Program 被拒绝：函数隐藏了具体字段

如果把 `&name.0` 抽成函数：

```rust
fn get_first(name: &(String, String)) -> &String {
    &name.0
}

fn main() {
    let mut name = (String::from("Ferris"), String::from("Rustacean"));

    let first = get_first(&name);
    name.1.push_str(", Esq.");

    println!("{first} {}", name.1);
}
```

这可能不能编译。

错误类似：

```text
cannot borrow `name.1` as mutable because it is also borrowed as immutable
```

从运行时行为看，这个程序是安全的。

`get_first` 只返回 `name.0` 的引用，修改 `name.1` 不会影响 `name.0`。

但 Rust 在检查 `get_first(&name)` 的调用时，只看函数签名：

```rust
fn get_first(name: &(String, String)) -> &String
```

这个签名只表达：

```text
返回值是从输入 name 里借出来的某个 String。
```

它没有表达“只借用了第 0 个字段”。

所以 borrow checker 保守地认为整个 `name` 都被借用了，包括 `name.1`。

## 如何处理这种 safe program

如果 Rust 因为保守分析拒绝安全程序，可以考虑：

- 内联表达式，直接写 `let first = &name.0;`。
- 调整数据结构，让需要分别借用的字段更明确。
- 使用标准库提供的安全抽象。
- 在后续章节学习 interior mutability，例如 `Cell`、`RefCell`。

不要第一反应就写 `unsafe`。

## Safe Program：修改 array 的不同元素

数组和 slice 上也会有类似问题。

比如我们想可变借用一个元素，同时不可变借用另一个元素：

```rust
fn main() {
    let mut a = [0, 1, 2, 3];

    let x = &mut a[1];
    let y = &a[2];

    *x += *y;
}
```

从运行时看，`a[1]` 和 `a[2]` 是不同位置，这段代码是安全的。

但 Rust 会拒绝。

原因是 borrow checker 不会为数组的每个索引维护独立 place。

它通常把数组元素看成：

```text
a[_]
```

也就是某个未知元素。

因为下标可能来自复杂计算：

```rust
let idx = a_complex_function();
let x = &mut a[idx];
```

编译器不能轻易知道 `idx` 到底是多少，所以会保守处理所有索引。

## 使用 `split_at_mut`

标准库提供了安全方法来表达“这两个区域不会重叠”：

```rust
fn main() {
    let mut a = [0, 1, 2, 3];

    let (a_l, a_r) = a.split_at_mut(2);
    let x = &mut a_l[1];
    let y = &a_r[0];

    *x += *y;
}
```

`split_at_mut(2)` 把 slice 分成两个不重叠的 mutable slice：

```text
a_l = [0, 1]
a_r = [2, 3]
```

所以：

```rust
let x = &mut a_l[1]; // 原来的 a[1]
let y = &a_r[0];     // 原来的 a[2]
```

Rust 可以确认它们来自不重叠的区域。

## `unsafe` 的位置

你可能会问：`split_at_mut` 内部怎么做到的？

很多底层标准库函数内部会使用 `unsafe` 和 raw pointer。

例如理论上可以这样写：

```rust
fn main() {
    let mut a = [0, 1, 2, 3];

    let x = &mut a[1] as *mut i32;
    let y = &a[2] as *const i32;

    unsafe {
        *x += *y;
    }
}
```

但这不是普通业务代码应该随便写的方式。

更好的策略是：

```text
如果 borrow checker 拒绝了一个你认为安全的模式，优先寻找标准库中已经封装好的安全 API。
```

例如：

- `split_at_mut`
- `get_mut`
- `split_first_mut`
- `chunks_mut`
- `iter_mut`

这些 API 可能在内部使用 `unsafe`，但它们对外提供的是安全接口。

## unsafe program 和 safe program 的区别

这一章反复强调一个判断：

```text
Rust 拒绝你的代码，不一定说明你的程序运行时一定有 bug。
```

可能有两类情况。

第一类：程序真的不安全。

例如：

- 返回局部变量的引用。
- 引用 `Vec` 的元素后，又 `push` 导致可能重新分配。
- 通过 shared reference 从集合里 move 出 `String`。

这种情况要修正程序设计。

第二类：程序是安全的，但 borrow checker 无法证明。

例如：

- 通过函数返回 tuple 某个字段的引用后，再修改另一个字段。
- 同时借用数组的不同下标。

这种情况要换成 borrow checker 能理解的表达方式，或者用标准库安全 API。

## 修 ownership error 的常用策略

### 1. 返回 ownership，而不是返回局部引用

错误：

```rust
fn f() -> &String {
    let s = String::from("hello");
    &s
}
```

正确：

```rust
fn f() -> String {
    String::from("hello")
}
```

### 2. 函数只要求真正需要的权限

如果函数只是读，不要写成 `&mut T` 或 `T`。

优先：

```rust
fn f(v: &[String]) {}
```

而不是：

```rust
fn f(v: &mut Vec<String>) {}
fn f(v: Vec<String>) {}
```

### 3. 缩短引用生命周期

错误：

```rust
let r = &v[0];
v.push(x);
println!("{r}");
```

正确：

```rust
let r = &v[0];
println!("{r}");
v.push(x);
```

### 4. 只复制需要的信息

如果只需要长度，就不要持有整个引用：

```rust
let largest_len = v.iter().max_by_key(|s| s.len()).unwrap().len();
```

而不是长期持有：

```rust
let largest = v.iter().max_by_key(|s| s.len()).unwrap();
```

### 5. 对非 Copy 类型，明确选择 borrow、clone 或 remove

只读：

```rust
let s = &v[0];
```

需要自己的 ownership：

```rust
let s = v[0].clone();
```

需要从集合中移出：

```rust
let s = v.remove(0);
```

### 6. 用标准库 API 表达不重叠借用

例如数组或 slice 的不同区域：

```rust
let (left, right) = slice.split_at_mut(mid);
```

## 本节总结

修 ownership error 的关键不是机械地加 `clone`、加 `mut`、改成 `&mut`。

真正的流程应该是：

1. 判断程序是否真的不安全。
2. 如果不安全，找到根本原因：生命周期不够、权限不够、aliasing 和 mutation 重叠、非法 move。
3. 如果程序安全但 Rust 无法证明，换成 Rust 能理解的表达方式。
4. 优先调整 API 和数据流。
5. 必要时使用标准库提供的安全抽象。

一句话：

```text
先理解数据应该由谁拥有、谁能读、谁能写、谁负责释放，再决定怎么修 ownership error。
```
